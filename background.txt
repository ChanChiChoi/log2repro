log2repro（错误日志 → 可运行复现代码生成器）
痛点：线上报错日志冗长，人工写复现脚本耗时长；新手常卡在环境依赖或数据构造上。
核心功能：
输入堆栈/日志片段，自动提取：关键变量、调用链、依赖版本
生成最小可运行复现脚本（Python/JS/Go）
自动附加 requirements.txt/Dockerfile/Mock 数据
支持一键提交为 GitHub Issue 模板
技术栈：Python + Tree-sitter + AST 解析 + LLM + Jinja2 + GitHub CLI

“实现日志到复现代码的自动化转换 pipeline，结合 AST 解析与 LLM 结构化生成；平均复现时间从 45min 缩短至 3min，已接入 3 个内部项目排障流程。”

🛡️ 二、对比 Sentry 的核心优势
Sentry 给“案发现场照片”，log2repro 给“可重播的案发现场”
Sentry 告诉你 TypeError: 'NoneType' object has no attribute 'id' 发生在 service.py:42，但不会告诉你 user 对象为什么是 None、外部 API 返回了什么、环境变量是否缺失。
log2repro 会从日志/堆栈中逆向提取：关键变量快照、依赖版本、网络请求 Mock，直接生成一个 pytest 可跑的脚本。
零侵入 & 遗留系统友好
老项目、第三方 SDK、外包代码、开源 Issue 经常无法接入 Sentry SDK。log2repro 直接吃纯文本/JSON 日志，开箱即用。
跳过“人工造数据”瓶颈
工程师 60% 的 debug 时间花在“猜参数、翻数据库、Mock 第三方”。log2repro 用 AST + LLM 自动推断边界条件，生成最小复现路径。
🔍 三、对比 Langfuse 的核心优势
通用性 vs 垂直性
Langfuse 专为 LLM Pipeline 设计（Trace/Prompt/Eval）。log2repro 是通用日志解析器，支持 Python/Node/Java/Go/C++ 堆栈，LLM 日志只是其中一类输入。
不关心“Prompt 怎么变”，只关心“报错怎么本地跑”
Langfuse 记录 LLM 调用链，但依然需要工程师手动把失败 Trace 转成本地脚本。log2repro 直接输出可执行代码，缩短复现链路。
对 LLM 场景的互补价值
Langfuse 记录失败调用 → 导出日志 → log2repro 解析 → 生成复现脚本 → 本地跑通 → 修复 Prompt/代码 → 回传 Langfuse 验证。形成闭环。
🤝 四、真正的护城河：如何证明它不是“套壳 AI”？

避坑与 MVP 聚焦建议
不要做全语言支持：MVP 先打透 Python + Node.js（生态最广、AST 工具最成熟），其他语言留 TODO。
绝不替代 Sentry/Langfuse：明确写 “Complementary tool, not a replacement”。提供 Webhook 对接示例，反而能蹭到它们的生态流量。
保留人工确认环节：LLM 生成的代码必须带 --review 模式，输出前高亮“推断变量”与“Mock 数据”，避免盲目信任。
